# 文档写作规范（WRITING-SKILL）

本文档是 AiMapUI 组件文档的写作规范，所有 `src/docs/content/` 下的 Markdown 文档必须遵循。

---

## 1. 一句话定位

每个组件文档开头用 **1 句话**描述它是什么、干什么，用业务语言而非技术行话。

**好**：`用圆的大小编码数值字段，实现分级统计地图。适合在区域面状底图上叠加显示各省/市的人口、GDP 等数值指标。`

**坏**：`BubbleLayer 是一个气泡图层组件，用于展示气泡数据。`

禁用模板：
- ❌ "XXX 是一个强大的/灵活的/功能丰富的组件"
- ❌ "XXX 组件提供了 XXX 的能力"

---

## 2. "何时使用 / 对比选型"

同类组件必须在文档开头用 `>` 引用块提供选型指引。

```markdown
> **何时选择：** 需要将数值映射为圆的大小时用 BubbleLayer；只需颜色编码不需要大小区分时用 [PointLayer](./point-layer)；需要热力渐变效果时用 [HeatmapLayer](./heatmap-layer)。
```

规则：
- 列出 2~3 个替代方案并说明各自适用场景
- 用 `[组件名](相对路径)` 做内部链接，不要写"详见第X节"

---

## 3. Props 描述规范

### 3.1 禁止属性名直译

每个 prop 描述必须包含以下**至少一项**，不能只写属性名的中文翻译：

- **行为语义**：这个 prop 具体做了什么、用户看到的效果是什么
- **边界值说明**：0 会怎样、超出范围会怎样、特殊值含义
- **省略时的默认行为**：不传这个 prop 时组件会做什么
- **与其他 prop 的依赖关系**：需要和哪个 prop 配合使用

| 评级 | 示例 | 问题 |
|------|------|------|
| ❌ 差 | `colorField`: "颜色映射字段" | 零增量信息，只是翻译 |
| ❌ 差 | `labelTrigger`: "标签触发方式" | 没说有哪几种触发方式、各自效果 |
| ✅ 好 | `labelTrigger`: "`'always'` 常驻显示标签，`'hover'` 时只在悬停时显示，大数据量下建议用 hover 减少文字碰撞" | 说明了选项、效果、性能建议 |
| ✅ 好 | `curvature`: "弧线弯曲程度。0 为直线，正值向一侧弯曲，负值向反方向弯曲" | 给出边界值和方向性 |
| ✅ 好 | `visible`: "图层可见性，设为 `false` 时图层数据保留但不渲染，可随时切回 `true`" | 说了"不渲染但数据保留"这个隐含行为 |

### 3.2 默认值必须标注

默认值不为 `undefined` 时必须在表格中标注。如果默认值来自内部逻辑（如 `sourceType ?? 'json'`），标明实际默认值而非写"-"。

### 3.3 复合类型必须展开或链接

`AnimateConfig`、`LayerEventPayload`、`GestureConfig` 等复合类型不能只写类型名，必须：
- 在文档中用子表展开定义，或
- 用 `[AnimateConfig](#animateconfig)` 锚链接到文内定义章节

### 3.4 "继承自" 声明

继承 LayerSchema 等基类的组件，Props 表只列出**专有属性和重定义属性**，开头声明：

```markdown
XXX 继承 [LayerSchema 公共属性](../layers/point-layer#公共属性)，此处仅列出专有属性和重定义属性。
```

不重复列举上游已有属性，避免文档冗余。

## 4. 文档结构规范

每篇文档按以下顺序排列，**按需取舍**（不是每篇都要全部章节）：

```
# 组件名
一句话定位 + 何时使用对比（> 引用块）

## 导入
import 代码块

## Props
按功能分组的数据表（数据源/视觉映射/交互/事件/公共属性）

### 子类型定义（如 AnimateConfig、PopupHeader 等）

## 示例
### 基础用法 — 业务场景名
### 进阶用法 — 业务场景名

## 注意事项
- 性能限制、大数据量建议
- 常见踩坑、默认行为差异
- 与上游/同类组件的行为差异

## 相关组件
- [ComponentA](./path) — 一句话说明区别
- [ComponentB](./path) — 一句话说明区别
```

### 4.1 禁止的结构

- ❌ 独立的"概述"段落重复组件名描述
- ❌ 示例标题用"示例1"、"高级示例"——必须用业务场景名
- ❌ "相关链接"章节列出外部 URL 但不解释用途

---

## 5. 示例规范

### 5.1 标题 = 业务场景名

```markdown
### 基础用法 — 省级人口气泡图
### 语义色板 + 悬停提示
### 大数据量优化
```

### 5.2 数据必须内联且可复现

`source` 数据必须给出 2~3 条真实坐标数据（北京/上海/广州等），不用 `data`、`cities` 这种抽象变量。

**好**：
```tsx
const bikePoints = [
  { lng: 116.397, lat: 39.908, count: 42 },
  { lng: 121.473, lat: 31.230, count: 91 },
]
```

**坏**：
```tsx
source={provinces}
// provinces 未定义，读者无法复现
```

### 5.3 每篇至少 2 个示例

- 1 个"基础用法"（核心功能最小代码）
- 1 个"进阶用法"（组合配置或性能优化）

---

## 6. 注意事项规范

用 Markdown 引用块语法，标注类型：

```markdown
> **提示：** `labelTrigger='hover'` 需配合 `hoverEffect` 开启才生效。

> **注意：** HexagonLayer 的默认 `sourceType` 为 `'json'`，与 BubbleLayer 的 `'geojson'` 不同。
```

标注类型：
- **提示** — 非显而易知的最佳实践
- **注意** — 可能导致 bug 的行为差异
- **性能** — 大数据量/性能相关建议

---

## 7. 交叉引用规范

- 用自然语流嵌入链接，不写"详见第X节"或"请参考XXX文档"
- 格式：`需要 XXX 时，可使用 [Component](./path) 代替`

**好**：`大数据量标注场景建议用 [PointLayer](../layers/point-layer) 代替`

**坏**：`更多内容请参考 PointLayer 文档`

---

## 8. 语气规范

- 写给**同行的开发者**，不是写给机器的说明书
- 用"你"不用"您"，不用"我们"
- 可以有判断性的表述：`大数据量场景下建议`、`不推荐同时使用`
- 避免空洞的形容词：灵活的、强大的、丰富的、完善的
- 英文专有名词保持原文：`source`、`Props`、`GeoJSON`、`callback`

---

## 9. 表格格式规范

### 9.1 Props 表分组

超过 10 个属性时，按功能分组为多个子表（数据源 / 视觉映射 / 交互 / 事件 / 公共属性），而不是一张超长表。

### 9.2 类型列中管道符的处理

联合类型如 `'normal' | 'additive' | 'subtractive'` 在表格中必须用行内代码包裹，渲染器会自动处理管道符转义。**不要**用 `\|` 手动转义。

### 9.3 必填标记

必填属性在默认值列写 `**必填**`，不要在类型列写。

---

## 10. 质量自检清单

提交前逐项确认：

- [ ] 一个组件的文档不少于 3 个章节（Props + 示例 + 注意事项）
- [ ] 每个 prop 描述包含增量信息（不只是属性名翻译）
- [ ] 复合类型已展开或锚链接
- [ ] 示例数据内联可复现
- [ ] 示例标题为业务场景名（非"示例1"）
- [ ] 同类组件有"何时选择"对比
- [ ] 至少 2 个交叉引用
- [ ] "注意事项"章节不为空
- [ ] 默认值标注正确（对照源码验证）
